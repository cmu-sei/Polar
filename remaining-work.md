### 1. What "migrated" means now

The old `AgentBuilder::new(..).with_health_check(..)` shape is gone (older commit messages describe it). Today (`polar-agent-builder/src/agent.rs`, `examples/hello_agent.rs`):

- The agent is a type implementing `PolarAgent`: `NAME`, `PURPOSE`, `NEEDS` (capabilities beyond the
  Cassini client), `SHUTDOWN_BUDGET`, `SECTIONS` (its own `polar-env` variables), `HELP`,
  `SELF_TEST`, `CASSINI_CLIENT`, and `async fn start(Configured)`.
- `main` is `polar_agent_builder::run::<A>()`. `run` answers `--help`, `--scaffold`, `--check --config
  FILE`, judges the configuration, and starts the agent; it never exits 0 for a started agent.
- Capabilities (`.with_graph_write()`, `.with_encryption()`, `.requires(..)`) replace
  `with_health_check`; health args come from capabilities and `POLAR_HEALTH_*`. The agent reads its own
  variables through `polar-env` declarations, not `std::env` (a `disallowed_methods` lint and a
  `clippy.toml` per crate enforce it).
- The infrastructure supervisor owns health, router, Cassini facade (reconnects with backoff and
  buffers offline publishes) and optionally crypto. `Respawned` / `InfrastructureRespawned` no
  longer exist. The domain supervisor keeps its half of `PrepareShutdown` -> drain ->
  `ProceedWithShutdown`, declares its own `SHUTDOWN_BUDGET`, and must treat the supervisor stopping as
  failure (exit non-zero so the Job restarts).
- A `Registered` arm must do health and nothing else, or guard what it spawns (`is_none()`), because
  `Registered` now fires on every registration, including a resume after a transient drop
  (see the FINDING item under "Gaps found 2026-10-08").
- Tests: `polar_agent_tests!(MyAgent)` in the agent's `agent.rs`.

- [ ] **GAP, MUST BE ADDRESSED (David, 2026-10-14): nothing checks that a certificate presented as an access credential carries the permission for what it is used to do.** The design says what a certificate's holder may communicate with is embedded in its SAN names (`p:` permissions, `cert-issuer/common/src/permission.rs`), resolved by `PermissionsActor` from the presented certificate plus supplemental permissions, and decided by Cedar in the nominal state (`polar-permissions`, `polar-policy`); the certificate is the floor and Cedar is the runtime nominal state. What is built: the credentials agent issues certificates with `p:` names from grants, runs Cedar over a requester's principal for secrets, and the builder admits signed documents by publisher. What is not: (1) agent certificates carry no `p:` names, because a Kubernetes workload needs no grant and none exists; (2) Cassini passes the peer's identity along with each message but, as far as grep of the broker shows, never decides whether a client may publish or subscribe to a topic, and never reads a permission; (3) no service-to-service call checks the caller's permission for the path. So any holder of a Polar-signed certificate can talk to any Polar service, which defeats the point of mTLS and zero trust for service-to-service traffic. Neo4j is the same and is accepted as a gap for now (next item). Shape agreed in principle, details to shake out: (a) know the pathways: each catalog workload declares the services and topics it needs, as it declares capabilities now, and the catalog is the source; (b) the certificate is the floor: the credentials agent issues each workload exactly those `p:` names from grants derived from the catalog, and refuses a request for more; (c) check at the receiving end: Cassini, and every service that receives requests, checks the presented certificate for the permission for the path, and consults Cedar when it is available (Cassini and cert-issuer run on the degraded floor alone, like the other bootstrap exceptions). To read before designing: how Cassini sessions, topics and `peer_identity` work in the broker; what the topics are and who publishes and subscribes to each; how `PermissionsActor` would be reached from Cassini, which is not a builder agent; what a grant for a workload looks like and where the catalog's grants are signed. ## Environment contract (`polar-env`), decided 2026-10-07

Design note: `docs/architecture/configuration.md` (what is built, the layers, who holds the configuration, the ConfigurationActor, the credentials agent, the schema export).

Principle: declare each environment variable once, with its type, default, documentation and whether it is secret. Reading, validating and describing it all derive from that one declaration, so the list of variables cannot exist apart from the code that reads it. A component groups its variables into a section (with any relations between them); the agent builder maps each capability to the sections it brings; one `check_environment` serves `build()`, the `polar-config-check` binary that `resolve.nu check` runs, and later each agent's own check mode. Whoever owns a fact owns the rule about it: the code owns the health relations, so they live in Rust and the render calls them; the deployment owns "grace period above budget", so that stays in Nushell. In progress as part of the health work (stages below); everything else here waits until the health work is done, then gets prioritised.

When the new session subscribes to a topic, the subscriber manager asks the session manager which sessions are held for its identity (the answer waits for any takeover still in progress) and claims `{old}:{topic}`, oldest first, delivering it to the new session ahead of live traffic; nothing is delivered for topics the new session does not subscribe to, and a different identity never inherits. Five tests in `tests/supersede.rs`; the expiry one fails with the expiry removed. A still-CONNECTED older session of the same identity (a restarted pod before dead-peer detection has noticed the old connection, up to about 60 s) is superseded too, done 2026-10-08: its connection is closed (unless it is the connection the new session registered on) and it is held like a detached one; the cost is that two live instances sharing one identity cannot both be served at once: a new registration displaces the older. An instance that asks to resume a session that was superseded (the old one, still running, reconnecting by itself) is given a session of its own but does NOT displace the one that took over, otherwise the two would take turns closing each other's connections (found by the first version of this test failing about half the time). Known gaps: (b) between claiming and the new subscriber attaching to the topic a message can reach both, or neither if other subscribers exist, a window of milliseconds that dedupe (step 4) closes; (c) no limit on what a holder queues, like any dead-letter queue here. Still NOT done: acknowledged deliveries (a message in flight when the connection dies is still lost).
